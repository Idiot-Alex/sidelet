# 列表分配优化与内存短测 · build 55

本轮减少时间轴重绘时的临时分配；三任务实机短测没有证明常驻内存下降，不将基准分配减少换算成 footprint 节省。

## 实现

- 主任务视图只缓存当前筛选和搜索的日期分组，工具栏“回到今天”、搜索计数和列表共享结果，不再每帧重复创建任务快照、筛选数组并排序分组。
- 缓存比较任务值和手动顺序，不只依赖服务 revision：侧栏编辑、完成、提醒和直接模型更新也会失效。模式、搜索、当地日期、时区、时钟回退及下一截止时间变化都会重新整理。
- 日期组共享一份排序后的数组，切片容量限定在各组边界，避免为每组额外复制任务。
- 只保留一个查询结果；没有历史查询缓存、全局缓存或 UI 节点缓存。视图销毁后可回收。代价是视图存续时保留 O(n) 的任务比较副本和分组结果，以减少多次重绘的临时分配；未承诺常驻占用必然降低。
- `TasksService.snapshot()` 仍返回独立副本，不改变调用方的数据所有权。未调整精灵动画、窗口隐藏策略、GC 参数或 SQLite。

## Mac 实机短测

build 54 原二进制与 build 55 优化二进制，均以 `-memory -main` 启动三条相同合成任务，相同窗口大小和主题，精灵及桌面任务开启。仅有一个测试实例同时运行；日常应用保持独立运行。没有读取或修改日常 SQLite。

使用 `scripts/profile-macos.py`，每个场景采样前等待 3 秒，每 3 秒采样一次，持续 15 秒（6 点），按进程 coalition 归属统计；两版测试都只有一个进程。下表为中位数，单位 MiB。

| 场景 | build 54 RSS / footprint | build 55 RSS / footprint |
| --- | --- | --- |
| 主窗口启动后稳定段 | 115.80 / 51.55 | 116.19 / 51.58 |
| 编辑并保存标题后 | 127.35 / 281.75 | 130.86 / 58.52 |
| 隐藏主窗口后 | 126.48 / 76.80 | 135.34 / 76.55 |

通过 Computer Use 执行编辑：先打开编辑器不改标题保存，再次打开后将标题粘贴为“内存对照测试”并保存，核实列表更新，然后使用“更多 → 隐藏窗口”。旧版第一次输入尝试未改变标题，因此第一次保存作为未修改保存处理，正式编辑结果使用 `before-saved`，不使用中间的 `before-edit` 采样。优化版重复了未修改保存和修改保存两步。两个测试实例已退出。

这是单轮顺序短测，操作之间的人工/工具耗时不同，非冷启动测试，也非严格等时稳态基准。旧版保存段 footprint 范围为 58.69–298.67 MiB，之后隐藏段回落至 76.80 MiB；优化版保存段为 58.52 MiB。不能把该瞬时峰值差异归因于列表缓存，峰值来源尚未定位。启动与隐藏段 footprint 基本持平，RSS 没有下降；当前可确认的收益是分配速率降低，不能宣称节省数百 MiB 或已解决峰值问题。

原始 CSV、环境、二进制 SHA、逐进程数据、汇总及安装记录：`build/results/list-memory-20261031/`。未测大任务量实机长期运行，未测 Windows 实机内存。
